# Scenario Sprite Animation

## Overview

Prompting a generic image model for "a sprite sheet, walk cycle, 8 frames" returns a picture of one. Real frame sequences come from routes picked by the control the task needs, not sprite size alone. This skill routes between lanes and carries the frame math; depth lives with siblings: `scenario-video` (video model families), `scenario-consistency` and `scenario-model-training` (one character across an action set), `scenario-game-assets` (statics, pixel cleanup, upscaling), `scenario-refine-loop` (iterate to brief). Connection and the core loop: the `scenario` skill. If a sibling skill named here is missing from your available skills, ask the user to install it (`npx skills add scenario-labs/skills --skill <name>`); unattended, proceed from tool schemas and flag the gap.

## Quick reference

| You need                              | Route                                                                                                                                                            |
| ------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Pixel cycles or VFX at 24 to 96px     | Purpose-trained animation model (`search` `"sprite animation"`; prefer a non-deprecated hit, else `recommend`): GIF preview, same-seed spritesheet re-run, slice |
| A seamless loop from a still          | First+last-frame video model (`search` `"first last frame"`): the same flattened still at both ends plus explicit motion language, extract, seam-check           |
| Poses hit at chosen moments           | Keyframe video model (`search` `"keyframes"`): pin pose stills to frame indices or timestamps, extract                                                           |
| Animate this sprite, larger or styled | Image-to-video on the flattened still, prompt anchored in a sprite-animation style with scripted motion beats; model choice per `scenario-video`                 |
| One character across an action set    | Turnaround plus reference-to-video per `scenario-consistency`; reuse the same references and settings for every action                                           |
| Frames to sheet, sheet to frames      | Tool models via `model_run`: `search` `"video to image"`, `"grid"`, `"slice"`, `"sequence"`                                                                      |

The authoring-time hits below show why the schema is the contract; re-discover rather than hardcode; searches take `public=true` (drop it only for the team's own trained models). Retro Diffusion Animation: a `style` enum picks the animation type and locks the canvas (`four_angle_walking` a four-direction walk, `walking_and_idle` a walk plus idle, both 48px; `small_sprites` 32px; `vfx` 24 to 96px). A requested 64px walk cycle is a schema violation, not a prompt problem: generate at the locked size and upscale after on a pixel-preserving route per `scenario-game-assets`. `returnSpritesheet` flips the output from animated GIF to spritesheet PNG: set an explicit `seed` on the preview run and repeat the identical payload with `returnSpritesheet` for the sheet, since a seedless preview cannot be re-run to match. Judge the preview from the downloaded file (`asset_download` with `format="gif"`: `asset_display` shows a still, and the png default flattens it to one frame). The `image` reference is converted to RGB without transparency, so flatten a transparent sprite onto a plain field deliberately. On the video side, keyframe pinning on a 24fps grid (FLUX.3 Keyframes), start plus end frames with an fps enum (LTX), and a style preset with a seed (PixVerse) were the live hits; turn prompt rewriting off (expansion and optimizer toggles) when exact wording carries the character or motion script; a deprecation tag names a replacement (`deprecated:model_x`) or stands bare, and the pointer can cross capabilities, so prefer the replacement only when its schema still covers the need. Video lanes are the expensive routes; `dry_run` prices a run before committing.

The frames pipeline is tool models run with `model_run`, not separate MCP tools: a video-to-image-sequence extractor (`extractAllFrames`, or every Nth frame via `frameInterval`; frames return in time order, and the grid maker keeps input order), a grid maker (up to 100 frames into a sheet, `backgroundColor` accepts `transparent`), a grid slicer (up to 6x6, no output-size parameter; tiles can come back resized, so check one with `asset_get`, and a resized tile or a sheet past 6x6 means cutting the downloaded sheet locally on the grid you counted), a sequence-to-video assembler (`model_scenario-image-seq-to-video`, a first-party id stable enough to name; fps 1 to 120, `loopCount`, `pingpong`, `gif` or `mp4`), and a pixel snapper (grid and palette cleanup; its color count is the only palette control in the cleanup chain, while Retro Diffusion Plus takes a reference palette image via `inputPalette` for palette-guided generation). Assembler fps is approximate (it may duplicate frames) and the only timing lever after generation, so plan frame counts up front.

## Worked example: a seamless idle loop from an approved or user-supplied character still

1. Create a dedicated collection for the job first (`collection_create`, tool catalog) and add every kept output as it lands. Flatten the character onto a plain field (a local edit is fine; reference inputs are documented as dropping transparency, assume video inputs do too) and `upload_asset` it. Confirm the lane and budget with the user; unattended, take them from the task instructions, else the cheapest lane that fits the brief, `dry_run` before every paid run.
2. `search` for first+last-frame video models, prefer a non-deprecated hit (or `recommend` with the loop requirement), then `model_schema_get`. The schema decides the levers: duration and fps enums, a camera lock such as `static`, an audio toggle, and a native loop flag where present, replacing the end-frame anchor: never send both (`dry_run` accepts combinations that still fail at run time).
3. `model_run` with the same still as first and last frame and a prompt that names the motion explicitly ("weight shifts, cloak sways; the character stays in place"). `jobs_wait` re-called with `pending_job_ids` while the job runs.
4. If the sprite needs alpha, extract first and run an image background remover on each frame (`search` `"background removal"`: the strongest hits are image models, and per-frame cutouts came back cleaner than the video-level pass in live runs; a remover's HD mode silently no-ops below its input floor; upscale past it for better mattes on glows); removing at video level before extraction also works when its output format carries alpha (`mov`, not `mp4`). Either way, verify alpha actually survived on one downloaded frame before batching: inline display composites it away, and a transparent request can come back stored in a container without alpha. Then extract with the video-to-image-sequence tool, reading the delivered duration, fps, and dimensions back with `asset_get` (requests are not always honored). Frame math: extracted count = delivered frames / `frameInterval`, endpoint-inclusive; where the schema exposes fps, generating at sprite cadence (8 to 12 fps: a cycle typically needs 8 to 16 frames) beats decimating after.
5. Seam-check: `asset_display` the first and last extracted frames. Near-identical means drop the duplicate endpoint before assembly; a visible jump means re-run (new `seed` where the schema has one, otherwise reworded motion). Unattended, accept when consecutive frames differ and the last leads back toward the first; allow one re-run, then flag and stop.
6. Finish and package: for pixel-art targets, snap each frame individually with the same color count and seed, never the assembled sheet (the snapper collapses a sheet to one global grid and throws away per-frame detail), then rescale the snapped frames to one common size on a nearest-neighbor route before assembly: each lands on its own native grid a few pixels apart, and padding without rescaling leaves the character pulsing in size across frames; sheet via the grid maker with `transparent` background; preview via sequence-to-video as GIF. `asset_download` frames with `format="png"` and the preview with `format="gif"`.

## Common mistakes

- One prompt at a generic image model for the whole sheet: frame sequences come only from purpose-trained animation and keyframe video models.
- Slicing the GIF preview: engine frames come from the same-seed `returnSpritesheet` re-run, sliced on the grid you counted; verify row order and facing visually before naming frames.
- Identical first and last frames with a bare prompt: that asks for a freeze, not a loop; the motion must be named.
- Assuming every model has a `seed`: many video schemas have none, so reproducibility there is per-asset, not per-run.
- Counting on an interpolation or pixelate filter: neither exists in the catalog; fps is the timing lever, and pixelating a non-pixel image is an img2img restyle per `scenario-game-assets`, then the pixel snapper.
- Photo upscalers on pixel frames: they invent texture; use the pixel-preserving routes in `scenario-game-assets`.
- Shipping a sheet unstepped: per-frame steps return new ids and order lives only in the lists you pass, so carry the frame-to-output mapping (never rebuild it from listings or timestamps), then composite and compare sheet to preview before delivery.
- Ping-pong or loop flags set blind: watch the downloaded GIF and match the assembler to it.
